🔡 Tokenization

The model doesn't read words — it reads tokens (roughly word fragments). "Hello world" might become [Hello, ▁world] or even [He, llo, ▁w, orld] depending on the tokenizer.

Hello ▁world !

⚡ Prefill (TTFT)

Before generating anything, the model processes your entire prompt in one big forward pass and stores the results in the KV cache. This is the first delay you feel — Time To First Token (TTFT).

📊 Logits & Sampling

After each forward pass the model outputs a logit score for every word in its vocabulary. Softmax turns these into probabilities, then sampling (or greedy argmax) picks the next token.

🔁 Autoregressive Bottleneck

The model generates exactly one token per forward pass. With a 7B model at 40 GB/s memory bandwidth that's roughly 1–2 tokens/s. The bottleneck is reading all the weights from memory, not arithmetic.

Key insight: Most of the time during decode the GPU/CPU is idle waiting for memory reads. The model's parameters need to be loaded from RAM for every single token — this is called being memory-bandwidth bound. katgpt-rs exploits this by generating multiple tokens in a single round.

🗜️ PFlash — Prefill Compression

Instead of feeding all prompt tokens through the full model, PFlash uses block-sparse attention to compress the prompt sequence by up to 21×, cutting TTFT (Time To First Token) by 29× in benchmarks. KV memory drops 93.8%.

✏️ DFlash — Draft Distributions

A small draft model (or the same model in a fast path) predicts marginal probability distributions for the next γ tokens all at once. These are not final tokens — they're candidate distributions.

✂️ Constraint Pruner

Before building the tree, a domain-specific rule removes tokens that are provably invalid (e.g., illegal moves in Sudoku, out-of-vocabulary words, constraint violations). This can eliminate 99%+ of branches.

🌲 DDTree — Best-First Candidate Tree

The filtered distributions are assembled into a token tree using best-first search. Each node is a candidate token; each path from root to leaf is a candidate sequence. Budget controls depth × width.

✅ Leviathan Verifier

The target model evaluates the tree. Each candidate token is accepted with probability min(1, p/q) where p is the target's distribution and q is the draft's. Rejected tokens are replaced by sampling the residual distribution. Output is identical to pure AR sampling.

🚀 Commit Multiple Tokens

On a good round with high acceptance rate, we commit γ+1 tokens in one verifier call. With γ=4 and 80% acceptance, we get ~3.6 tokens per round instead of 1. Combined with fused kernels and a tiny micro-model, this reaches 10k–30k tok/s.

Why does this preserve quality? The Leviathan verifier guarantees that the final output distribution is identical to what the target model would have produced with standard autoregressive decoding. Speed comes from amortizing the expensive forward pass across multiple tokens, not from degrading output quality.

Section 6

DDTree — Candidate Token Tree

This is the core data structure in katgpt-rs. Each node is a candidate token. The verifier walks from root to a leaf, accepting or rejecting at each level.

How it's built

1. DFlash produces a probability distribution over the vocabulary for each depth level (depth 0 = next token, depth 1 = token after that…).
2. ConstraintPruner removes invalid tokens from each distribution.
3. A best-first heap expands nodes until the budget is exhausted — high-probability paths get expanded first.

How it's verified

The target model runs a single batched forward pass over all leaf nodes. For each node, if p(token)/q(token) ≥ U[0,1] the token is accepted. On rejection, a residual sample ends the path and provides the corrected token.

Sudoku example

For a Sudoku solver, each token is a digit (1–9) for a cell. The ConstraintPruner eliminates digits that already appear in the same row/column/box. The DDTree only contains valid partial solutions — invalid branches are never evaluated.

💣 Bomber Arena

In the Bomber arena demo, katgpt-rs acts as a game AI agent. The action space (move up/down/left/right, place bomb, wait) is the "vocabulary". The ConstraintPruner blocks moves that would walk into a bomb blast radius. The DDTree explores multi-step action sequences before committing.

Result: Bomber HL score +177 vs random agent −55. NFSP/MCTS duality achieves 75% win rate vs MCTS's 8%.

🧠 Why does the same architecture work for both?

Both text generation and game-playing are sequential decision problems under uncertainty. In both cases:

  • There is a state (conversation history / board state)
  • There is an action space (next word / next move)
  • Some actions are invalid (grammar constraints / game rules)
  • A model scores candidate actions
  • We want to find a good sequence of actions quickly

Speculative decoding + DDTree + ConstraintPruner solves this efficiently regardless of whether "tokens" are English words or game moves.

Section 8

Glossary for Developers

New to LLMs? Here's a plain-English explanation of every term used in this demo, with small examples where helpful.

Token
The atomic unit of text that an LLM processes. A token is roughly ¾ of a word on average — but tokenization is vocabulary-specific. Numbers, punctuation, and rare words may each become multiple tokens.
"Hello world!" → [Hello] [▁world] [!]
Tokenizer
The preprocessing step that converts raw text into a sequence of integer token IDs (and back again). katgpt-rs uses a custom BPE tokenizer with vocab size 27 (a–z + BOS) for its micro-model. Large LLMs use vocabularies of 32k–128k tokens.
encode("cat") → [3, 1, 20]
Prefill
The phase where the model processes all prompt tokens before generating any output. Results are stored in the KV cache so they don't need to be recomputed. Long prompts = expensive prefill. The time until the first output token is called TTFT (Time To First Token).
KV Cache
Attention computes a Key and Value matrix for every token. Once computed, these are cached — so decoding new tokens only needs to compute K/V for the new token, not re-read the entire history. Without KV cache, decoding would be O(N²).
Decode / Autoregressive Decoding
The loop where the model generates one token at a time by feeding its own output back as input. Standard decoding is strictly serial — each token depends on all previous tokens. katgpt-rs breaks this with speculative decoding.
Logits
The raw, unnormalized scores the model assigns to every possible next token. A softmax converts them to a probability distribution. The token with the highest logit is the most likely next token (greedy).
logits: [cat: 2.1, dog: 1.8, the: -0.3, …]
Sampling
How the next token is chosen from the logit distribution. Common strategies: greedy (always pick top-1), top-k (sample from top-k tokens), top-p / nucleus (sample from smallest set covering p% probability). katgpt-rs uses categorical + residual sampling in the verifier.
Speculative Decoding
A technique where a cheap draft model predicts γ future tokens, and the expensive target model verifies them in one batched pass. Accepted tokens are committed; rejected tokens trigger a correction. Output quality is provably identical to pure autoregressive sampling (Leviathan et al. 2022).
Draft Model (DFlash)
A small, fast model that predicts marginal probability distributions for the next γ tokens. It doesn't need to be perfect — just good enough to have high acceptance rate. In katgpt-rs, DFlash runs the same micro-transformer in a faster path.
Constraint Pruner
A deterministic rule that marks token IDs as valid or invalid before building the candidate tree. In Sudoku, a pruner removes digits already used in the same row/column/box. In text generation, a pruner might enforce grammar or domain vocabulary.
cell(0,0) used: {1,3,5} → valid: {2,4,6,7,8,9}
DDTree (Candidate Token Tree)
A best-first token tree built from the draft distributions after pruning. Each node is a (token, depth, parent_path, score). A max-heap expands the highest-scoring nodes first. The tree compactly represents all candidate sequences the verifier might accept.
Verifier (LeviathanVerifier)
The target model evaluated on the draft's candidate tree. It computes target probabilities p(token) and accepts each draft token with probability min(1, p/q). If rejected, samples from max(0, p − q). The bonus token at full acceptance gives γ+1 tokens per round.
Tree Search
Exploring a branching space of possibilities systematically. In chess engines (Minimax, MCTS), tree search finds good moves by looking ahead. In katgpt-rs, DDTree search finds good token sequences by looking ahead γ steps — using draft distributions instead of full forward passes.
Acceptance Rate (α)
The fraction of draft tokens that pass the verifier's p/q test. With α = 0.8 and γ = 4, expected accepted tokens per round = α + α² + α³ + α⁴ + 1 ≈ 3.95. Higher α = more tokens committed per verifier call = higher throughput.
Memory Bandwidth Bound
LLM decode is limited by how fast weights can be read from RAM, not by arithmetic throughput. Each forward pass reads all model weights — for a 7B model that's ~14 GB. At 40 GB/s bandwidth: ~2 tokens/s. This is why batching (or speculative decoding) dramatically improves efficiency.
BPE (Byte-Pair Encoding)
The most common tokenization algorithm. It iteratively merges the most frequent adjacent byte/character pairs to build a vocabulary. Given enough merges, common words become single tokens and rare words are split into subword pieces.
"playing" → [play] [ing] (if "ing" is frequent)
